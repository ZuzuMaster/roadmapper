#### Description:

For those in the world who struggle to keep track of tasks, steps, and the order of them, navigating projects, learning courses, etc., can be an inconvenient and grueling task. Many common solutions, such as task managers and to-do lists, lack one thing: a clear line of events. This is the problem that Roadmapper attempts to solve. Roadmapper is a simple web application designed to allow users to create and edit roadmaps of tasks for projects, courses, etc. Using Python, Flask, SQLite, JavaScript, HTML, and CSS, Roadmapper attempts to fill this gap in common solutions by providing an easy and extremely simple way to manage your pathways.

Once an account is created and logged into on Roadmapper, users are greeted by a clean and simple homepage that displays their current stats across all roadmaps, the link to an "/about" page with instructions and details, and a list of all created roadmaps by that user (along with a few other small features). To add a new roadmap, the user can simply click the + button, allowing them to create a new untitled roadmap that can later be edited. Once being edited, the user can use the interface to create nodes and connect them to create a continuous line of events. These nodes can then individually be edited with links, titles, and also moved around the roadmap itself. Each roadmap has a progress bar signifying how much of the roadmap has been finished or completed—along with a fun confetti effect once one is entirely finished!

Under the hood, Roadmapper operates on a lightweight architecture using Flask, Jinja, and SQLite. The relational database utilizes four core tables: users, roadmaps, nodes, and connections, storing everything from encrypted credentials to individual node (x, y) grid coordinates and completion states. When a user submits a form on the frontend—such as updating a node's title via the "/customize_node" route—Flask handles the request in app.py, validating user ownership with helper functions like get_owned_node() and executing parameterized SQL statements to prevent injection attacks. Once the database is updated, the application redirects the user back to the roadmap view, where fresh data is queried and passed to Jinja templates to render the updated state. On top of all of this, user authentication states are securely maintained across requests using Flask-Session backed by the filesystem, ensuring that certain routes stay inaccessible without an active login session.

One of the main technical hurdles I faced when developing was handling node connections. My initial method involved no separate connections table in my SQLite database, and instead I implemented two columns to the nodes table: "previous" and "next". Using these attributes, I attempted to track a node's position and order in line through a linked list system, rendering each node as such when queried. However, this soon led to many problems, including inefficient lookups, complex deletion/creation systems, and a lack of support for multiple nodes being connected to multiple nodes. Without the ability to store multiple entries as neither "previous" nor "next", every roadmap was forced into a single, linear list of tasks. To fix this, I decided to create a new table that would have the only task of storing connections by a node's ID. Using this new table, a single node could be connected to multiple other nodes, and vice-versa. This also allowed for much easier systems when deleting and creating nodes, along with rendering connections. Instead of needed to sort each node into a linked list prior to sending the data to Jinja, the new system allowed for pure connections to be sent to Jinja along with the nodes, giving much more simplicity to the backend system.

One major design trade-off I encountered during development was deciding how users can position and layout their nodes on their roadmap. While a free-form, drag-and-drop canvas interface would offer maximum visual customization, it introduces significant complexity in collisions, overlaps, data storage, rendering, etc. Although that concept wasn't out of reach for my current abilities and knowledge, I opted for a structured grid system using "x" & "y" columns and rows managed through the "move_node" route and forms. This restricted nodes to a clean 3 column layout. While this sacrifices some fluid visuals, it guarantees organized rendering and keeps database logic robust.

Building Roadmapper was an extremely insightful exercise in designing a full-stack application from scratch, deepening my experience and knowledge with databases, sessions, backend, and frontend. Currently, the application has certain limitations such as the robust grid, lack of multi-user collaboration, etc. If I were to continue developing Roadmapper, I would integrate a JavaScript canvas to allow free-form dragging and possibly add sharing of roadmaps. Although these limitations exist, the entire project made me realize with a great deal the struggles, fun, and learning that comes out of experiences like these.
